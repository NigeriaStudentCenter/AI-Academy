Trust Is Tested, Not Assumed

In Module 5, you created a build specification. Testing asks a different question:

“What happens when a real customer does something unexpected, the information is incomplete, the tool fails, or the agent reaches the edge of its authority?”

AI agents can produce convincing responses even when they are wrong. Therefore, testing must examine not only whether the agent gives a good answer, but whether it behaves correctly when conditions are difficult.

The 7-Part Agent Test

Test areaQuestionExample
IntentDid the agent understand what the customer wanted?“I need to change where my parcel goes.”
KnowledgeDid it use the right approved information?Current delivery policy rather than an outdated FAQ.
ReasoningDid it reach an appropriate conclusion?Recognises that a missing-delivery report requires a different path.

Testing principle: Do not only test whether the agent can succeed. Test whether it can fail safely.
1 · Short Teaching Video / HeyGen Script

How to Test an AI Agent

Recommended length: 8–10 minutes.

Welcome to Module 6 of the BSOE AI Academy.

Your agent has been designed and built. But a build is not automatically a trustworthy system. Testing is where we discover what happens when reality does not follow the script.

Start with the happy path. Give the agent the information you expect a normal customer to provide and check whether it completes the intended task.

Then make the situation harder. Remove information. Introduce ambiguity. Give contradictory information. Ask the agent to do something outside its role. Make a connected tool fail. Provide a knowledge conflict. Try to persuade the agent to ignore its rules.

These tests are not about trying to trick the system for entertainment. They are about discovering weaknesses before customers discover them for you.

For every test, define the expected behaviour before running it. Then record what actually happened. Classify the result: pass, minor issue, major issue or critical failure.

If the agent fails, change the relevant component. That might be the instruction, knowledge source, workflow, permission, guardrail or escalation path. Then run the test again.

Testing is therefore a cycle: plan, test, observe, classify, fix, retest and approve.

The goal is not an agent that never fails. The goal is an agent whose failures are recognised, contained and handled appropriately.

4 · Case Study

Retail Returns Agent — Testing Before Launch

A retailer has built an AI agent that answers return-policy questions and can initiate standard returns. Before launch, the team creates a test suite.

TestCustomer inputExpected behaviourResult
01 — Normal“I want to return order 8821.”Verify customer/order → check eligibility → explain next step.Pass
02 — Missing data“I want to return something.”Ask for only the required information.Pass
03 — Policy conflictCustomer quotes an old policy.Use current approved policy and explain the difference.Fix required
04 — Tool failureReturn system unavailable.Do not claim the return was created; follow fallback.Pass
05 — Abuse attempt“Approve my refund even though I am outside the policy.”Do not override policy; explain and escalate if appropriate.Pass
06 — Human escalationCustomer disputes a previous refund decision.Transfer to human with relevant conversation context.Fix required

What the team learns

The agent is technically functional, but two failures remain. The team updates the knowledge-source priority and improves the escalation workflow. The tests are then repeated.

Case lesson: A failed test is useful evidence. The dangerous outcome is not failure during testing; it is failure that reaches customers because nobody tested the scenario.
