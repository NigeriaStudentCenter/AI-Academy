Jargon, in plain words

New techy words for this lesson, explained like you're 12 — with when and why you'd use them.
Skill
A saved, reusable rule-book the AI follows automatically for a task. Like a recipe card the chef must follow every time, so the dish is always the same. When: when you need the same high standard every time. Why: consistency and compliance, with no re-explaining.
Instructions / system prompt
The standing directions you give the AI up front that shape everything it does. Like the job description you hand a new worker on day one.
Custom GPT / Project
A saved AI helper you set up once with instructions and knowledge, then reuse. Like a labelled toolbox set up for one job. (A "Custom GPT" is ChatGPT's version; a "Project" is Claude's.)
Knowledge file
Documents you give the helper to rely on — a brand guide, a policy, an FAQ. Like the staff handbook kept on the worker's desk.
SKILL.md
A simple text file that packages a skill's rules in a standard format (used by developer tools). The written recipe card itself.
Trigger
What makes a skill kick in — a keyword, a file type, a kind of task. "When someone orders dessert, use the dessert recipe."
What you'll be able to do: build a reusable AI helper that follows your rules every time — a Custom GPT or Project with instructions and a knowledge file — and understand how a Skill (a SKILL.md) packages those rules for consistency.
The scenario: A support team's replies sound different from every person — some off-brand, some missing the legal disclaimer. Instead of re-explaining the rules each time, they build a Skill that enforces the tone, structure and disclaimer automatically. Now every reply is on-brand, every time.

1What a Skill actually is

A plain prompt teaches the AI something once. A Skill saves the rules so the AI applies them every time, automatically. It's built from instructions (the standing rules) plus an optional knowledge file (documents to rely on, like your style guide). Package that up and you get a helper that never forgets the standard.

When it's used: on-brand customer replies, reports that always follow a template, code that follows the team's style, marking that always uses the same rubric. Why it's used: consistency, compliance, and huge time savings — you set the rules once.

3Go deeper — with code (optional)

Skip if you like — you've already built a rule-following helper above. For the technical view, a Skill can be written as a small SKILL.md file that developer tools load. Read it like a labelled recipe card:

Go deeper · a SKILL.md example 
---
name: brand-reply
description: Draft a customer reply in our house style, always with the disclaimer.
---
# Rules
- Warm, plain English. No jargon.
- Keep it under 120 words.
- If it's about refunds, link to the refunds policy.
- Always end with the legal disclaimer text.

# Example
Input: "My order is late."
Output: a short, warm apology + next step + the disclaimer.

The name and description help the tool know when to trigger the skill; the rules and example steer the output. Always follow the official docs for the exact format — it changes.

Guardrails — safety & ethics

  • Never put secrets in a Skill. No passwords, API keys, or private customer data in instructions or knowledge — especially if the helper is shared.
  • Test before you trust it. Try real, tricky cases; make sure the rules actually hold.
  • Version your rules. Keep track of changes so you can undo a bad edit.
  • Keep a human review step for anything customer-facing or high-stakes.
Try this today (5 min): build a tiny Custom GPT or Project that enforces one checklist or house style, then give it a task and watch it obey the rules.
Common mistake: piling in too many or conflicting rules. Keep them short, clear and non-contradictory — and test them.
